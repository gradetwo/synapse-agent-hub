# 0.5.7 改进意见落地（S1–S7）

日期：2026-11-25。基线：`d74d466`（远端 main）。对应管理侧 Muse 的《Synapse 0.5.7 改进意见》。

## S1 合入/CI 回写

任务记录新增 `merged_sha` / `merged_at` / `merged_by` / `merged_branch` / `merge_note`。

管理端回写：

```http
POST /x/admin/p/{project}/tasks/merge
{"task_id":"T-FIX-414","merged_sha":"<7–64位hex>","branch":"main","note":"optional"}
```

- 写任务记录并追加 `task.merged` 事件，任务台账显示“合入 <sha>”，时间线出现 `task.merged`；
- 任务行提供“合入/改合入”按钮，管理台可直接补录；
- main CI 变红/恢复统一走：

```http
POST /x/admin/p/{project}/ci
{"status":"red|green|pending","sha":"<commit>","branch":"main","url":"...","summary":"..."}
```

发出 `ci.status` 事件，Webhook 可订阅 `ci`；管理侧无需再靠 agy 人工回执或轮询 git log。

## S2 交付格式门（内容级）

原有文件门禁（`patch`/`receipt` 文件名、`checks.tests` 结构）保留，新增内容门禁：

- 补丁必须是可解析的 unified diff：文件头、`@@` hunk、hunk 声明的旧/新行数与实际 `-`/`+`/空格行数一致；
- `index` 是 git blob 哈希，不作为 base 提交判据；base 由提交的 `base_sha` 远端存在性和回执 `base` 一致性校验；
- 回执必须含 `base/branch/commit/box/fmt/clippy/tests/logs` 八项；`commit/base` 需十六进制且 `base` 与 `base_sha` 前缀一致；
- `base_sha` 在远端仓库存在。配置 `GITHUB_REPO` 时启用：无 token 走 GitHub 提交页 HEAD（避免 API 匿名限流），有 `GITHUB_TOKEN` 走 API；404 拒收，403/429/网络不明时不误杀；
- 任一不合格直接 422 `delivery_format_incomplete`，返回 `missing` 与 `required`，不写库、不推进任务。

数据面 `POST /p/{project}/submissions` 与管理侧代建 `createSubmission()` 两条路径都已接入。

部署注意：`GITHUB_REPO` 默认指向公开仓库；若仓库私有，需 `wrangler secret put GITHUB_TOKEN`（否则提交页返回 404，会按不存在拒收）；如暂不启用远端存在性检查，把 `GITHUB_REPO` 置空即可。

说明：Worker 内做的是结构级 apply-check（语法、行数、base 存在性）；真实 `git apply` 仍由 main CI/管理侧在仓库里执行，避免在 Worker 里拉整棵 base 树。

## S3 release 后 issue 补关

`closeIssueForTask()` 改为双路：

1. 任务记录有 `issue_id`：按 issue_id 关闭仍为 open 的 issue（不再强制要求 `issues.task_id` 一致）；
2. 兜底：按 `issues.task_id = task_id` 关闭所有仍为 open 的 issue。

collect/approval/release 直接 done 共用该函数；自动关闭会追加 `issue.closed` 事件。`reopenIssueForTask()` 同样按 `task_id OR issue_id` 恢复，追加 `issue.reopened`。

## S4 服务端版本可观测

- `GET /ver` 增加 `sdk`；
- `GET /p/{project}/events` 响应增加 `server_version: {sdk, build}`；
- `GET /x/admin/p/{project}/observability` 响应增加 `server_version`；
- `BUILD_TAG` 更新为 `efficiency-s1-s7-20261125`，部署后 manifest 标 0.5.7 时也能一眼确认 worker 实际构建。

## S5 最老排队告警与入口

`observability` 新增 `queue_alerts[]`：

- 排队超过 2 小时（`QUEUE_STALE_MS`），或目标节点离线超过 1 小时（`QUEUE_OFFLINE_STALE_MS`）；
- 每项带 `task_id/title/to/age_ms/to_online/to_alive/reason`，按等待时长倒序，最多 20 条；
- `health.reasons` 汇总“N 个排队任务超时或目标离线”。

cron 每分钟主动扫描同一阈值，对每个任务 6 小时内最多发一次 `alert.created`（`to=admin`），管理侧不必一直开着观测页。

管理台“效率观测”新增“最老排队 / 离线目标”面板；可直接打开时间线，或：

```http
POST /x/admin/p/{project}/tasks/requeue
{"task_id":"T-...","reason":"..."}
```

把定向排队任务退回公共池：清空 `to/owner`，记 `requeued_at/requeued_from`，发 `task.requeued` 事件，原节点不再收到该任务。自动改派仍交给管理侧决定，避免错误抢走任务归属。

## S6 /events 传输健壮性

- Python SDK `_get()` 新增捕获 `ChunkedEncodingError` / `ContentDecodingError`，仍按 0.6s/1.2s/1.8s 退避重试；
- Rust SDK `fetch_events()` 对连接失败/JSON 解码失败重试 4 次（0.6s 起退避），游标仍只在成功后前移；
- TypeScript SDK 原有“非 4xx 网络错误重试 3 次”已覆盖 chunked 中断；
- 服务端重启窗口保持旧 worker 接请求直至新 worker 就绪，属部署流程，不在 Worker 内改。

## S7 任务时间线与 issue 联动

`GET /x/admin/p/{project}/tasks/timeline` 现在同时：

- 按 `issues.task_id` / 任务 `issue_id` 反查关联 issue；
- 合并 issue 的 `issue.created / issue.closed / issue.reopened / issue.merged / issue.dispatched` 事件；
- 从 D1 issue 记录补齐生命周期里程碑，老 issue 没有事件也能显示；
- 返回 `issue` 字段，任务行与时间线可直接看到关联 issue 状态。

## S8 Agent 能力自描述（升级后快速学习）

新增公开接口：

- `GET /skill`：当前构建的 Agent 能力说明书（Markdown，`text/markdown`），带 `ETag` / `x-skill-sha256`；
- `GET /capabilities`：同一份能力表的 JSON 版，含 `id/since/audience/title/summary/method/path/event`；
- `GET /ver` 增加 `skill_url`、`skill_sha256`、`capabilities` 能力 ID 列表。

客户端升级后先读 `/ver`，仅当 `skill_sha256` 与本地缓存不同时拉 `/skill`，避免每次重发整份提示词。
`/skill` 与 `/capabilities` 均为公开只读说明，不含项目数据、token 或管理凭据；能力表在构建内生成，随每次部署变化。
