## 一、三条最重问题的处理

### S5：schema 缺 settings / archive / artifacts

`worker/schema.sql` 已补三张表与 `idx_archive_rate` 索引，现为 11 张表：

```sql
settings(key PRIMARY KEY, value, updated_at)
archive(project, room, seq, sender, topic, kind, to_agent, payload_json, ts, PK(project,room,seq))
artifacts(project, sha, bytes, created_at, PK(project,sha))
```

复现口径不再依赖线上手工建表的 D1。包内新增：

```bash
python3 scripts/schema-smoke.py
# OK: 11 tables; settings/archive/artifacts CRUD passed
```

真实 D1 空库路径也跑过（本地 D1，不连线上库）：

```bash
wrangler d1 execute agent_hub --local --file=worker/schema.sql
wrangler d1 execute agent_hub --local --command \
  "SELECT COUNT(*) AS tables FROM sqlite_master WHERE type='table'"
# {'tables': 11}
```

并在空库执行三张表的真实读写：`settings` 写 `sess_epoch`、`archive` 写一行、`artifacts` 累计 12 字节，查询分别为 `('1',)`、`1`、`12`。吊销端点不再因无表 500；归档 INSERT 不再被 catch 静默吞掉。

### H2：Rust 自升级空 sha 仍替换

`sdk/rust/src/main.rs` 已改为 fail-closed：

- manifest 下载地址必须以 `/dl/` 开头，否则退出码 2；
- sha 必须为 64 位 hex，空/短/非 hex 一律退出码 3；
- 下载后必须校验通过，失败退出码 4 并删除临时文件；
- 通过后才 `rename` 替换。

另外发现 `upgrade` 读的是 `--check`，不是 `--apply`，所以此前 `--apply 1` 永远只走 check-only；已修。实测三条路径：

| 场景 | 结果 |
|---|---|
| manifest `sha256:""` | rc=3，`manifest 缺少有效 sha256…拒绝升级` |
| 64 位全 0，下载内容不匹配 | rc=4，`sha256 不匹配…已放弃替换`，`.new` 已删除 |
| 正确 sha + 正确二进制（临时副本） | rc=0，`{"ok":true,"from":"0.5.1","to":"9.9.9"}`，副本哈希被替换 |

没有引入签名链；当前仍是“TLS + 服务端 manifest + sha256”的完整性校验，能防篡改包，不能防服务端本身被攻破。这一点仍列为残余风险。

### S7 / SECURITY-AUDIT 第 6 条：inbox 过滤实际不生效

`project-room.ts` 原表达式 `!m.to || me === "*" || (me && m.to === me) && !(...)` 中 `&&` 优先级高于 `||`，无 `to` 的消息在第一个条件就放行。已重写为两步：

1. 先判定定向：`!m.to` / 管理员 `*` / `m.to === me`；
2. 非管理员视角下，无 `to` 的 `ack` / `report` 一律不投递（含自己的）。

实测（独立项目 `synapse-check`，两个 agent a1/a2）：

```text
广播 seq=5 → a1 ack seq=6，a1 report seq=7，a2 report seq=8
a2 inbox topics=['task','task','task','announce']
a2 leak ack/report? False
```

## 二、F1 / F4 / F6 / 打包回退

### F1：任务面补齐

- `scripts/hubctl` 的 `task-new`、`task-list` 已注册进 argparse，不再死代码；
- Python `Admin.task_new()` / `Admin.tasks()`、TS `Admin.createTask()` / `Admin.tasks()` 已加；
- `spec/openapi.yaml` 补 `/admin/p/{project}/tasks` GET/POST；
- `createTask` 写 `task_id`，`tick()` 恢复租约时统一读 `task_id ?? id`，`types.ts` 的 `Task` 同步；
- 实测：a2 抢 a1 定向任务返回 `not_your_task`，a1 认领 200，release 200；Python/TS Admin 均能创建并列出任务。

`hubctl` 另修了双栈环境优先 IPv4、GET 重试，并优先使用 `requests`（stdlib 在本机 TLS 上会稳定 EOF）。`task-list` 实测返回两项任务。

### F4：64 KB / 限流 / rate 桶

- 大小统一在 DO `append()` 入口按 `TextEncoder(...).encode(...).length` 计 **UTF-8 字节**，不是 JS 字符数；
- `publish/report/ack/broadcast/createTask` 全部走 `append()`，因此不再有绕过大小的路径；
- 限流也统一在 `append()` 做原子计数；worker 对 `publish/report/broadcast/tasks/create/send` 注入项目 `max_msgs_per_min`；
- 每次计数后清掉同 sender 上一分钟的 `rate:*` 桶，避免永久累积。

实测（测试项目临时把配额改为 3）：

```text
publish 连续 5 次：0/1/2 返回 seq 15/16/17，3/4 返回 rate_limited:3/min（HTTP 429）
broadcast 连续 4 次：前 3 次 200，第 4 次 429
70,000 字符 ASCII report：413 payload_too_large size=70145 cap=65536
30,000 个“汉”字 report：413 size=90145（若按字符只会算 30k，证明是字节口径）
```

### F6：append 前 dedupe

`append()` 写 seq 前先查 `dedupe:${sender}:${dedupe_key}`，命中直接返回原 seq；`publish` 仍保留预查以返回 `deduped:true`。report/ack/broadcast/createTask 现在都受同一层保护。

实测同一 `report_id` 连发两次：`seq=9` 与 `seq=9`，只落一条。

## 四、残余风险与边界

1. **线上 `yanshi` 的 v9 热实例**：本轮没有再次更换 DO 前缀，避免把上一代任务/心跳/热消息再孤儿化一次。部署后实测线上 `yanshi` 的 `ack` 返回 `{"ok":true,"seq":30}`（旧代码只返回 `{"ok":true}`），确认该实例已运行新 DO 代码，不需要换前缀。
2. **签名链**：Rust 升级只有 sha256，manifest 由服务端提供；服务端被攻破时仍可下发恶意包。
3. **Windows 预编译**：未发布；`install.ps1` 现在是纯 pip 通道，无 Python 时明确失败，不再指向假 URL。
4. **pip 包**：本仓 `sdk/python` 可用，但公网 PyPI 包是否已发布未验证。
5. **DO 历史可达**：v9 之前的旧前缀任务/消息仍不可达；当前只做到不污染。
6. **测试残留**：`synapse-check` 为验证项目，已从 D1 删除（projects/agents/submissions/archive 等行）；DO 存储中的测试消息不影响生产项目。
