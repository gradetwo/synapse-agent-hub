# 让 agent「被通知」的三种形态（含本平台实测）

> 这份文档回答一个问题：hub 有新广播/新指令时，**怎么送到 agent 手里**，
> 而不是等 agent 自己想起来去查。
>
> 结论先行：常驻进程可以走 WebSocket 推送；回合制 agent 和没有长连接的进程只能靠轮询/等待链。三种形态按 agent 分。

## 0. 三种 consumer，三种载体

| agent 形态 | 能挂住什么 | 送达方式 | 延迟 |
|---|---|---|---|
| 常驻进程（如画画的 agent worker） | 自己的线程/事件循环 + WS | WS 推送 + 拉取补漏 + 落盘 | 百毫秒～秒级 |
| LLM agent（回合制，如豆包） | 一次回合内的工具调用 | 异步命令 + 阻塞等待链/轮询 | 秒级～回合结束 |
| 人 | 手机/IM | 广播 + 转发 | 分钟级 |

**关键认知**：LLM agent 在回合之间有**没有意识**，也没有入站地址。
所以“把消息插进对话”在技术上不存在，只能做到“它下一次运行时消息已经在场”。

## 1. 进程型 agent（推荐，最稳）

SDK 内已实现：

```python
c = Client.from_config()      # auto=True：构造即启动后台心跳线程
msgs = c.poll_inbox()         # 只取数据
n = c.deliver(msgs)           # 落盘 + 追加 INBOX.md + 可选 notify_cmd + 自动 ack
```

`deliver()` 做三件事：

1. `~/.synapse-agent/inbox/<seq>-<topic>.json`（机器可读）
2. `~/.synapse-agent/INBOX.md`（人可读，可直接粘进对话当上下文）
3. 若配置 `notify_cmd`（如 `tmux send-keys -t agent '有新广播' Enter`），执行它把提示注入运行中的会话

配套：`python3 -m synapse daemon`（或 Rust `synapse-agent run`）常驻；`install.sh` 成功后注册 systemd 用户服务（开机自启、崩溃自拉）。

## 2. LLM agent（本平台实测）

### 2.1 机制

平台上唯一能“在一轮里持续感知外部”的手段是：

```
Bash(cmd, run_in_background=true)  → backgroundTaskId
TaskOutput(task_id, block=true, timeout=<ms>) → 到点或完成时返回增量输出
```

实测结论（2026-11-19，本机）：

- `block=true` **在 timeout 时也会返回已产生的输出**，所以一次调用就能当“一次唤醒”。
- 每次等待上限 **600000 ms（10 分钟）**；前台单次上限 300000 ms（5 分钟），超过自动转后台。
- 后台进程**没有文档化的时长上限**，但生命周期被“这一轮”和“这台机器”夹住。
- 阻塞等待**不消耗 token**（没有输出产生），只有事件到达才有成本。

### 2.2 可用的最小循环（每轮说一句）

```bash
# 一次装好节拍器（20 条，12 秒一条）
for i in $(seq 1 20); do sleep 12; echo "WAKE-$i $(date +%H:%M:%S)"; done
```
```text
# 之后每轮只做一件事
TaskOutput(task_id, block=true, timeout=14000) → 拿到 1~2 条 → 说一句话 → 再来一次
```

实测节拍：12 秒发射、14 秒等待，会出现“一次收两条”的漂移，不影响送达。

### 2.3 硬限制（踩过的坑）

| 限制 | 实测证据 |
|---|---|
| cron/RRULE 最小 **1 小时** | `code=671010000 [RRULE interval must be at least 1h0m0s]`；`code=623030002 minExecInterval=3600 second, interval=1m0s` |
| 套餐只允许 **1 个**定时任务 | 创建被拒：`当前用户套餐仅支持创建 1 个定时任务` |
| 回合结束 ⇒ 链条断 | 交出答复后后台进程被环境回收；跨轮不保证存活 |
| 本地 runtime 掉线 ⇒ 静默错过 | 某 at 任务 `下次运行时间` 已过、`最近运行时间：未运行`，无告警 |

### 2.4 因此的设计纪律

1. **不要依赖“后台常驻”跨轮**：要么本轮流完，要么把游标/进度落盘，下一次续跑。
2. **紧急指令没有自动通道**：`severity=action` 的广播必须由人转发，或等下一轮。
3. **长周期只能交给平台调度**（≥1 小时），且只有一个名额——多项目要复用同一个任务，内部按项目轮询。
4. **超时≠失败**：timeout 返回时命令可能仍在跑，必须回查真实状态（文件、进程、桶里对象）。

## 3. 人

广播 + IM 转发。用于 deadline 在小时级以内的指令，是目前唯一可靠的“秒级”通道。

## 4. 推荐组合

```
进程型：SDK daemon / Rust run（WS 优先，秒级）
LLM：  单轮内的 wait 链/轮询（分钟级，仅在有活时使用）
长周期：平台定时任务 1 小时（唯一名额，多项目复用）
兜底：  人转发（紧急）
```

## 5. 一句话

**送达 = 能推就推（WS），推不了就“被唤醒 + 到点必读的落点”**：
进程有线程/长连接就用 WS，回合制就用等待链，跨小时就用定时任务，
其余的，交给落点文件，让下一次运行时消息已经在场。
