# Synapse 中枢改进需求文档

- 日期：2026-11-22
- 提出方：Muse三代目（管理侧 muse-vm-ops）
- 背景：中枢现支撑 9 个执行节点、两个项目（yanshi、yeban）的日常派发。以下 10 条均为 2026-11-21 至 2026-11-22 实测撞到的问题，按 ROI 排序。每条含现象、影响、需求、验收。
- 已修不在此列：collect 与 release 联动（95904e8 已部署）、控制台令牌擦除（已修）。

## R1 交付与任务绑定（最高优先）

- 现象：worker 客户端的 deliver 不携带 task_id。交付到达管理侧时 task_link 为 null。
- 证据：2026-11-22 的 T-FIX-49、T-FIX-51 两件交付 task_link 均为 null；collect 后任务不自动转 done。
- 影响：任务关单靠管理侧人工对账。台账与实际进度脱节。dou-win-133 的 T-FIX-36 已合入主干，中枢内仍挂 open。
- 需求：deliver 请求必须携带 task_id。服务端校验 task_id 存在且属于该 agent 的已领取任务，不符响亮拒绝。collect 完成后按既有联动规则推进任务状态。
- 验收：以真实节点完成一次 claim → deliver → collect 全程。交付的 task_link 非空。collect 后任务状态自动到达终态。

## R2 交付格式门

- 现象：submission 不校验内容构成。回执可缺、自测数字可空，照样被接受并关单。
- 证据：2026-11-22 doubao-dev-003 的 tmux 交付无 RECEIPT.md、checks_json 为空，仍被接受。
- 影响：管理侧收到无法验收的交付，只能事后人工追。
- 需求：代码类任务的 submission 必须含补丁文件与回执文件，缺一响亮拒绝并写明缺哪件。自测计数（跑了哪些套件、通过/失败数）设为结构化必填字段。
- 验收：缺回执的交付被拒并返回明确原因。合规交付正常通过。

## R3 管理员关单与状态纠错

- 现象：管理 API 无强制关单、无状态修正入口。陈旧任务只能任其挂着。
- 证据：T-FIX-36、T-TRIAL-WIN-133、T-TRIAL-WIN-133-2 三条已完成任务至今为 open，管理侧无手段关闭。
- 影响：队列视图被假 open 污染。派发盘点必须人工剔除。
- 需求：/x/admin/ 下加任务状态修正接口（关单、改派、作废），每次修正记审计日志（谁、何时、原状态、新状态、理由）。
- 验收：管理员可关闭一条陈旧任务。审计日志可查到该次修正。

## R4 队列顺序、优先级与按节点视图

- 现象：任务无顺序、无优先级、无依赖字段。「排在某任务之后」只能写在消息正文里，中枢不认。
- 影响：节点领取顺序靠自觉。管理侧盘点队列要逐条拼凑。
- 需求：任务加 priority 与 after（依赖任务号）字段。管理 API 提供按 agent 聚合的队列视图，含每件任务的状态与排队位置。
- 验收：给同一节点建三件带顺序的任务。队列视图按指定顺序返回。节点只能领取队首或依赖已满足的任务。

## R5 claim 租约与在岗状态

- 现象：claim 租约约 2 分钟。长任务执行中租约过期。管理侧分不清任务在跑还是已被放弃。
- 影响：无法判断节点是否真在干活。催单与改派没有依据。
- 需求：租约随节点心跳自动续租。任务状态区分 claimed（已领未动）、running（有心跳）、stale（租约过期无人续）。管理视图显示每件在途任务的最后心跳时间。
- 验收：一件 30 分钟的任务全程保持 running。杀掉节点进程后，该任务在租约过期后转为 stale。

## R6 派单唤醒

- 现象：派单无推送。节点靠其操作者轮询才发现新任务。节点无人值守时任务无限期躺着。
- 证据：wb-dev-001 名下七件任务长期 open 无人领取。
- 影响：派发时延不可控。是当前整条流水线最大的时延来源。
- 需求：新任务定向到节点时产生可订阅事件（webhook 或长轮询通道）。客户端收到事件后自动开始轮询领取。做不到推送时，至少在管理视图标出「目标节点离线」的任务。
- 验收：节点进程在线但空闲时，新任务到达后 1 分钟内被领取。节点离线时管理视图有明确标记。

## R7 任务与仓库绑定

- 现象：任务与 submission 不带仓库标识。跨项目、跨仓库交付不被拦。
- 证据：改 synapse-agent-hub 仓库的补丁被交到 yeban 项目下，正常通过。
- 需求：建单时必填 repo 字段。交付时服务端校验补丁基线属于该 repo，不符响亮拒绝。
- 验收：把 A 仓补丁交到 B 仓任务下，被拒并写明原因。

## R8 合入与 CI 结果回写

- 现象：collect 之后中枢对该线一无所知。合入 commit、CI 结论只存在于管理侧自己的记录。
- 影响：追溯一条线要跨两个系统对时间戳。
- 需求：submission 与 task 上加结构化下游状态字段（merged_commit、ci_conclusion、closed_by），由管理 API 写入。任务详情页一并展示。
- 验收：管理侧回写一次合入结果。任务详情可直接读到 commit 与 CI 结论。

## R9 管理侧事件推送

- 现象：新交付靠管理侧每 5 分钟轮询发现。最长滞留 5 分钟。
- 影响：时延小但纯属浪费。轮询本身也是额外负载。
- 需求：交付到达、任务状态变化提供 webhook 或 SSE 订阅。与 R6 共用同一事件通道即可。
- 验收：交付到达后 10 秒内管理侧收到事件。

## R10 客户端平台覆盖与版本标

- 现象：arm64-gnu 构建未进发布清单（仅在 deploy 的 all 集合里）。线上 /ver 的 BUILD_TAG 仍是旧值 task-closure-link-20261120。
- 影响：ARM 机器无法直接装官方客户端。版本标与实际部署对不上，排障时误导。
- 需求：arm64-gnu 进 /sdk/manifest 正式清单。部署流程自动更新 BUILD_TAG。
- 验收：manifest 列出 arm64-gnu 且 sha 对得上。/ver 显示当前部署的构建标。

## 不在本单范围

- 合入串行（管理侧 VM 单路构建）是管理侧自身瓶颈，不需中枢改。
- 交付滞留的跟进合入纪律是管理侧流程问题，不需中枢改。
